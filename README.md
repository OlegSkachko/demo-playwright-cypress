# Lumen Store: Playwright vs Cypress

Демо-магазин (React + Django + Postgres + WebSocket) и **один и тот же набор пользовательских сценариев**, написанный на Playwright и на Cypress. Цель проекта — сравнить фреймворки на живом приложении и выбрать один для регулярных прогонов на проде.

```
.
├── frontend/          React 18 + Vite: каталог, корзина, оформление заказа, история заказов, уведомления
├── backend/           Django 5 + DRF + Channels: API, токен-авторизация, WebSocket /ws/notifications/
├── e2e/
│   ├── playwright/    сценарии UC-01…UC-15 на Playwright
│   └── cypress/       те же сценарии UC-01…UC-14 на Cypress
├── docker-compose.yml postgres + redis + backend + frontend (nginx)
└── .github/workflows/e2e-prod.yml   запуск тестов на проде по кнопке
```

## Быстрый старт

```bash
docker compose up --build
```

| Что | Адрес |
|---|---|
| Магазин | http://localhost:8080 |
| Django admin | http://localhost:8080/admin (`admin` / `admin`) |
| API напрямую | http://localhost:8000/api/products/ |

При старте бэкенд сам выполняет миграции и заполняет базу (`python manage.py seed`, команда идемпотентна).

### Два сценария

- **Гость**: смотрит каталог, ищет и фильтрует товары, кладёт их в корзину (корзина хранится в `localStorage`). Купить не может: кнопка «Оформить заказ» заблокирована, а `/checkout` перенаправляет на вход.
- **Авторизованный пользователь**: корзина хранится на сервере, гостевая корзина переносится в неё при входе. Может оплатить заказ и видит историю в разделе «Мои заказы».

### WebSocket-уведомления

`ws://<host>/ws/notifications/?token=<api-token>`
- гость получает общие рассылки (`broadcast`);
- пользователь дополнительно получает личные уведомления: `order.created`, `order.status`;
- после оплаты заказ сам проходит статусы «Оплачен» → «Собирается» → «Передан в доставку» (пауза между шагами задаётся через `ORDER_STATUS_DELAY`, по умолчанию 3 с). Статус обновляется на странице без перезагрузки;
- рассылка всем от админа: `POST /api/notifications/broadcast/ {"text": "..."}`.

### Запуск e2e

```bash
cd e2e
npm install
npx playwright install chromium    # браузер для Playwright, ставится один раз
```

| Задача | Playwright | Cypress |
|---|---|---|
| Прогон в консоли | `npm run pw` | `npm run cy` |
| Интерактивный режим | `npm run pw:ui` | `npm run cy:ui` |
| Интерактивный режим в браузере | `npm run pw:ui:web` → http://localhost:9323 | `npm run cy:ui:web` → сразу открывается Chrome |
| С видимым браузером | `npm run pw:headed` | `npm run cy:headed` |
| Открыть HTML-отчёт | `npm run pw:report` | `npm run cy:report` |

По умолчанию тесты идут на `http://localhost:8080` (docker compose).

### Запуск на проде

Тесты не трогают базу напрямую: данные готовятся только через публичный API. Перед каждым авторизованным сценарием тест очищает корзину тестового аккаунта. Поэтому их можно запускать против любого стенда:

```bash
cd e2e
BASE_URL=https://shop.example.com \
TEST_USER_EMAIL=qa@lumen.shop TEST_USER_PASSWORD=******** \
npm run pw          # или npm run cy
```

> На реальном проде понадобятся отдельный тестовый аккаунт и тестовый режим оплаты. Каждый прогон UC-09, UC-13, UC-14 и UC-15 создаёт по заказу.

**По кнопке, без локальной установки.** GitHub → Actions → **«E2E на проде»** → *Run workflow*: выберите фреймворк (`both` / `playwright` / `cypress`) и при необходимости URL. Нужно один раз задать переменную репозитория `PROD_URL` и секреты `TEST_USER_EMAIL` и `TEST_USER_PASSWORD`. HTML-отчёты прикрепляются к прогону как артефакты. В файле workflow есть закомментированный `schedule` для ежедневного прогона.

## Сравнение: что выяснилось на этом проекте

| | Playwright | Cypress |
|---|---|---|
| Результат на демо | 15/15 | 14/14 |
| Время полного прогона (локально) | ~26 с (15 тестов) | ~19 с (14 тестов) |
| Ожидания | автоматические (`expect(...).toHave*`) | автоматические (`should`) |
| Стиль кода | `async/await`, обычный JS | цепочки команд, свои правила работы с переменными (`.then`, алиасы) |
| Подготовка данных через API | фикстура `request` | `cy.request` |
| Доступ к WebSocket-фреймам | **есть из коробки** (`page.on('websocket')`, UC-15) | нет, только через плагины или обходные пути |
| Несколько вкладок или пользователей в одном тесте | есть (`context.newPage()`) | нет, одна вкладка |
| Браузеры | Chromium, Firefox, WebKit (Safari) | Chrome, Edge, Firefox, Electron; без WebKit |
| Отладка | Trace Viewer: снимки DOM, сеть и консоль на каждом шаге, видео | Time-travel в интерактивном раннере, скриншоты |
| Отчёт | встроенный HTML-репортер | нужен плагин (тут `cypress-mochawesome-reporter`) |
| Параллельность | встроенная, бесплатная | в одном процессе нет, параллельность через Cypress Cloud |

Что всплыло по ходу работы:

- **Cypress нашёл настоящий баг вёрстки.** `overflow-x: hidden` на корневом контейнере ломал `position: sticky` у шапки, и при прокрутке она уезжала. Проверка видимости в Cypress это поймала (UC-07), а Playwright тест пропустил. Баг исправлен (`overflow-x: clip`).
- **Подвох Cypress с алиасами.** Начиная с Cypress 12, `.as()` по умолчанию заново ищет элемент в DOM при каждом обращении. Чтобы запомнить значение, нужен `{ type: 'static' }`.
- **Подвох Playwright 1.49 и Node 24.** При `"type": "module"` в `package.json` раннер молча зависает, поэтому в `e2e/package.json` его нет.
- Playwright запускается с `workers: 1`: все авторизованные сценарии используют одного тестового пользователя с общей серверной корзиной. Если завести по аккаунту на воркер, Playwright можно распараллелить, и он станет быстрее Cypress.

## Разработка без Docker

```bash
# backend (Python 3.12; без POSTGRES_DB используется SQLite, без REDIS_URL — in-memory channel layer)
cd backend && python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate && python manage.py seed
daphne -p 8000 config.asgi:application

# frontend (Vite проксирует /api и /ws на :8000)
cd frontend && npm install && npm run dev       # http://localhost:5173

# тесты против dev-сервера
cd e2e && BASE_URL=http://localhost:5173 npm run pw
```
